Enterprise Agent · Terminology Layer

让 Agent 听懂
你们公司的黑话

企业级 Agent 落地的第一道墙不是推理能力，是词汇：行业术语口径不一、内部黑话无迹可查、产品代号一词多义。 本方案把这个问题拆成实体归一化 + 定义注入，用一套可版本化、可自增长的术语层解决。

链路：AC 自动机别名精确匹配（主力）→ 消歧归一 → 分层注入 L1 定义。生产版另含向量召回兜底与 MCP 活查询。
§01

问题定义

企业 Agent 要听懂三类词汇，每类的失败模式不同，治理手段也不同。

TYPE-A
行业术语
IRR · FHIR · prior auth

模型可能懂个大概，但口径未必与公司一致——答得出来，答得不准。

风险：口径错位（公司 MRR ≠ 教科书 MRR）

TYPE-B
公司内部黑话
星环 · 上会 · 小蜜

模型完全不懂，且只存在于口头和私聊——语料里根本没有。

风险：训练数据缺失（公开语料不存在）

TYPE-C
产品名 / 代号 / 缩写
TDH · ACP · v3 内部代号

短文本，embedding 几乎无信号；同名冲突多，一词多义。

风险：向量检索失效 + 同形歧义

问题本质 实体归一化 （多说法 → 一概念） + 定义注入 （LLM 缺的是定义，不是推理力）
§02

调研核心结论

五条结论均有案例实证，是后续所有设计的依据。没有一条来自推测。

0/ 16 家微调

没有一家微调

Hebbia（金融尽调）、Carta（临床抽象）、Thomson Reuters（法律）、Warp（自改进 agent）全部走运行时注入 + 可版本化文本工件：当天可改、可审查、可回滚、换模型不丢。

依据 [11][12][13][14]
−49%检索失败率

词典精确匹配 > 向量（对短术语）

Anthropic 官方实测：BM25 词法匹配对缩写、代号、错误码最有效（例 "TS-999"），embedding 无信号；hybrid + rerank 失败率降 67%。知识库 <200k token 时直接全量塞 prompt 即可。

依据 [1] Contextual Retrieval
80%系统提示词被删除

渐进式披露是大量术语的正确姿势

Anthropic 为 Claude 5 代模型删掉 Claude Code 80% 以上系统提示词，无效果损失——过度约束比欠约束更伤。Skills 三层 token 预算：索引 ~50 / 速查 ~500 / 详情 2000+。

依据 [3][7]
1个 improver 闭环

术语库是复利资产，靠闭环自增长

Warp 模式：版本化文件 + PR 评审 + 定时 improver agent 挖掘工作现场反馈、提最小修改、人审合并，下次运行自动继承。反馈采集多一步提交动作都会丢信号。

依据 [14]
98–99%专家一致率

验收 = 专家一致率，不是准确率

eSentire 与资深专家判断一致率 95%；Carta inter-rater reliability 98–99% 达行业金标准。术语理解的唯一金指标：agent 判断与领域专家判断的一致程度。

依据 [5][12]

企业调研（500+ 技术负责人）：数据访问与质量（42%）是 agent 落地最大瓶颈之一——
术语理解不是 prompt 技巧问题，是企业知识供给管道问题。

§04

术语库设计

单条术语是一个 YAML 文件；整个术语库是 Git 仓库——diff 可审、可回滚、agent 可提 PR，这是“复利资产”的物理形态。

terms/data-intel/platform.yamlterm-0042 · v3
# 术语条目：不止是定义，还有 why、示例、口径脚本 canonical: 星环数据平台 aliases: [星环, TDH平台, 数仓] business_line: 数据智能部 # 消歧路由 + 权限分域 definition: | 公司内部统一数仓，底层 Transwarp TDH…… why: | 销售口中“星环”指平台整体；技术口可能指 TDH 组件。写 why 是为模型能泛化推理。 examples: - q: 把上季度星环的用量拉出来 a: 查 tdm.usage_monthly 按部门聚合 scripts: usage_query: tools/query_usage.py # 口径的确定性执行 disambiguation: - context: 销售/售前会话 means: 平台整体 - context: 数据研发会话 means: TDH 组件 source: [{by: zhang.s@corp, date: 2026-08-30}] confidence: 0.9 version: 3 # PR 次数 = 版本，Git 即审计日志
L0 索引~50 tok/条识别层常驻（不占 LLM 窗口）

canonical + 触发词（aliases）+ 一句话。喂给 AC 自动机做匹配，是机器用的。

L1 速查~500 tok/条命中即注入 prompt

canonical + definition + 业务线。单次对话实际命中 3~5 条，注入成本 < 3k token。

L2 详情2000+ tok/条仅 L1 不够判断时展开

全量：why + examples + scripts + 消歧规则 + 来源。

▲ 三层渐进披露对应 Skills 三层 token 预算（50 / 500 / 2000+）。L0 不占模型上下文；500 条术语的 L1 按对话实际命中量注入。

04-1Git 治理

YAML 按业务线分目录（权限分域的自然边界），条目变更走 PR 评审，版本即审计日志。

04-2权威口径只走 PR

人工评审合并；memory 只存运行时学到的用户偏好，绝不承担权威术语表职责（会漂移）。

04-3条目写法

写原则 + why + 干净示例，不穷举规则——示例会被模型极仔细地模仿，必须正确。

§05

查询时五步链路

识别

AC 自动机（如 pyahocorasick）对 aliases 做多模式精确匹配——主力；向量召回仅做兜底，处理错别字与“飞书云文档 → 知识库”这类口语变体。

消歧

同形术语（如“小蜜”）按 disambiguation.context + 对话历史 + 提问者业务线路由；无法消歧时反问用户，而不是猜。

注入

按 §06 选型表分流（常驻 / Skill 展开 / MCP 活查）；同对话已注入的术语不重复展开，省 token。

未命中许可 防幻觉关键

system prompt 明确：“术语未命中且无把握时，声明‘未找到权威定义’而非猜测”——Anthropic prompt 指南直接指出这能显著降幻觉。

引用

回答中对关键术语标注来源条目（Hebbia 逐格引用模式），领域专家可逐条纠错，错误可归因。

§06

注入机制选型

五种机制不是竞争关系，是分工关系——按术语的量、变化频率、结构化程度分流。

机制擅长不擅长术语场景
Prompt 直塞少量、核心、稳定；零基建；确定必进上下文规模化吃窗口；改一次全量改；无版本治理★★★★★（<百条核心表）
Skill 三层渐进披露成体系、任务耦合；索引常驻命中展开；Git 版本化依赖 description 质量；静态不随使用演化★★★★★（中大型术语库首选）
MCP 活查询真值源在系统里、高频变、量大（SKU / 产品目录 / 代码表）；权限可审计只管“拿到”不管“解释”；每次查询有延迟成本★★★★★（动态结构化术语）
Memory 沉淀运行中习得的约定、用户纠错；跨会话（复杂任务 +39%）模型自主提炼会漂移；不能当权威标准★★★★★（沉淀层，须可查看可编辑可关闭）
Context editing长任务不爆窗（token −84%）纯垃圾回收，不注入知识★★★★★（安全垫）
ONE-LINE DECISION 核心少量 → 直塞；成体系大库 → Skill 三层；海量高频变结构化 → MCP 活查 + Skill 消歧（MCP 负责「拿到」，Skill 负责「解释」）；用户纠错 → memory；context editing 兜底。
§07

术语库自增长闭环

冷启动靠人工 + 文档挖掘，跑起来之后靠这个闭环自增长——Warp 已在开源仓上验证的模式（数千次代码评审、数百贡献者）。

① 反馈就地采集会话内纠正 / PR 评论
零提交摩擦
② improver 定时挖掘拉取累积反馈，对比 agent 行为
与专家纠正；挖未识别词
③ 生成最小 diff单条目级 PR
降低人审负担
候选流转
④ 人工评审护栏：默认反馈可能有错
agent 先 sanity check
⑤ 合并入库版本化文件
Git 历史即审计日志
⑥ 自动继承下次运行即生效
新术语 T+1 可用
回到 ① 持续采集
↻ 可验证领域加回归 harness：术语库每轮变更先跑参考语料对比
护栏一：反馈默认可能有错

improver 需带上下文 sanity check，过滤反馈来源可信度。

护栏二：人审终审

agent 只提最小 diff，合并权永远在人。

护栏三：登记前置

新产品上线 checklist 强制含“术语登记”，否则闭环只能消化存量。

§08

验收指标与 eval 基准

LAYER 1 · 识别层
术语命中率

recall / precision。可离线单测——词典匹配是确定性的。

LAYER 2 · 消歧层
路由正确率

同形术语按上下文路由的正确率，构造跨业务线对话用例。

LAYER 3 · 端到端
专家一致率

对齐 eSentire 95% / Carta 98–99% 模式。唯一金指标。

LAYER 4 · 归因
错误定位

定位到术语表 / 识别 / 注入 / 检索哪一环，避免只看聚合分。

建行业专属基准（30~50 条标注 query 起步），随模型升级与术语库更新持续加码，新模型与旧模型 head-to-head 对测（Hebbia 模式）。术语关系复杂时（产品→子产品→部门→负责人）后备 GraphRAG 实体图增强，不在 POC 范围。

§10

前置条件与风险

“

对 agent 而言，没写下来且不可访问的东西就不存在。”公司黑话只存在于口头、私聊和 DM，agent 永远学不到。需要默认公开 + 少量清晰安全边界的信息架构（Slack / Anthropic 共同强调）——这是决定术语库上限的组织前置条件。

memory 漂移污染权威口径

权威定义只走 PR 通道；memory 只存偏好，且可查看 / 可编辑 / 可关闭。

别名爆炸导致 AC 误命中

L0 索引带业务线过滤；命中后消歧层反问确认。

术语表全量塞爆上下文

三层披露硬预算（50 / 500 / 2000）；context editing 兜底。

反馈质量差带偏术语库

improver 只提最小 diff + 人审终审 + 回归 harness。

换模型后行为变化

eval 基准 head-to-head 对测通过后才切换（Hebbia 模式）。
