# 跨组专题：18 仓横向模式提炼（Java + 图编排 + 财务合规视角）

> 输入：`profiles/` 全部 18 份档案（A 组：ai-hedge-fund / FinRobot / TradingAgents / Vibe-Trading；B 组：DB-GPT / SQLBot / supersonic / WrenAI / DataAgent / data-formulator；C 组：cline / codex / gemini-cli / opencode / OpenHands / claude-code-sourcemap；D 组：gpt-researcher / browser-use）。组内细节见 `dimensions/A-金融交易组.md`、`B-BI数据组.md`、`C-编码agent组.md`，本文不重复，只做跨组提炼。硬约束回顾：① agent 服务独立部署、与业务服务通过 API 通信；② 图编排工作流；③ 硬性审批/审计/合规。每条模式标注来源档案与章节，档案内已有路径级证据的直接沿用。

## 专题一：多 agent 拓扑——什么场景选什么，图上怎么表达

### 1.1 拓扑选型目录（六个原型）

**T1 层级投票（并行独立 + 算术合成）**——谁在用：ai-hedge-fund（档案 §2）。怎么实现：agent 间零通信，各自对同一 PIT 快照投票产 Signal，代码按 model_weights 加权合成（abstain 同时剔除分子分母），LLM 人格与量化模型同一 ABC 可混编。适用：多检查项合成一个结论、要求确定性与零串扰（月结审查、报销初审）。弱点：无推理交换，共识质量完全取决于权重。

**T2 辩论-裁决（固定轮次对抗 + deep 模型裁判）**——谁在用：TradingAgents（档案 §2）。怎么实现：bull/bear 交替互驳（共享 history + 对手最新论点），纯计数器终止（2×轮次，token 可预算），裁判节点用 deep 模型出结构化裁决。适用：需要对抗推理暴露单边盲区（报销争议、异常调查）。弱点：无收敛判断，输出零强制力（停在观点层，A 组档案 §3 风控光谱①②级）。

**T3 并行研究 + 独立审查 + 授权合同**——谁在用：Vibe-Trading Swarm DAG（档案 §2/§5）。怎么实现：YAML preset 声明 agents（角色/工具白名单/iterations-timeout-token 三重预算）+ tasks（DAG + input_from 上游 summary 注入），分层并发；生成与审查分离（CRO 独立审不写结论）；权威不来自 agent 而来自人工授权的 mandate。适用：高风险产出需独立质检 + 权威与智能解耦（付款建议、终审）。

**T4 群聊派工（消息驱动路由）**——谁在用：FinRobot V0（档案 §2）。Leader 以 `[员工名] 指令` 文本协议 + 正则匹配触发嵌套会话，TERMINATE 字符串终止。定位：**跨组反面教材**——路由正确性 = LLM 遵守格式 × 字符串匹配，不可静态验证、终止不可预算、每轮 reset 无状态。动态派工需求应上移到图编排层做受控路由。

**T5 事件溯源订阅（反应式多角色）**——谁在用：OpenHands（档案 §2）。怎么实现：append-only EventStream 为唯一真相源，controller/runtime/UI/memory 是各自订阅者（每订阅者单线程池保序、互不阻塞）；delegate 子 agent 由父转发事件、start_id 切片区分审计归属。适用：多角色关注同一执行流（执行者/审计器/风控器/推送器），天然获得完整审计轨迹。弱点：delegate 共享流，审计归属靠事件区间推断，不如显式 correlation-id 清晰。

**T6 子 agent 扇出（受控并行分片）**——谁在用：DB-GPT `dispatch_parallel_tasks`（档案 §2）、claude-code subagent（档案 §8）。怎么实现（DB-GPT 隔离模型五件套）：派生会话 ID（含 batch_id 防跨批泄漏）+ 独立记忆 + 独立工具集（只读过滤）+ 共享只读资源 + 产物走旁路/仅压缩结论进主上下文（8000 字符摘要上限）+ 单失败不炸批；claude-code 侧：上下文 fork 清不完整 tool_use、工具池按画像裁剪、`allowedTools` 整体替换（父会话临时授权不泄漏给子 agent）、权限模式继承规则、只读 agent 剔除冗余上下文省 token。适用：并行对账/多科目取数/多凭证核验——财务场景最常用的拓扑。

### 1.2 图编排（约束②）下的表达：动态性的四个合法位置

18 仓证明「动态性 ≠ 放弃静态可审计性」，合法位置只有四个：
1. **静态图 + 条件边循环**（TradingAgents 档案 §2）：拓扑固定，辩论回环用条件边 + 计数终止；MsgClear 节点裁剪跨阶段上下文（只把报告 str 传下游）——「固定轮次」是图上可预算的循环，path_map 全量映射防 fall-through。
2. **静态图 + 计划驱动路由**（DataAgent 档案 §2.2）：LLM 规划产物 Plan JSON（schema 强约束 + 工具白名单校验 + 必填参数检查）作为状态变量驱动 dispatcher，步进游标由代码执行——「LLM 只能从白名单里选下一步做什么，路由决策本身是确定性代码」。这是财务「先出方案→审批→逐步执行」的最直接图表达：计划可校验、可审批、可整体重生成（校验失败带 PLAN_VALIDATION_ERROR 回 Planner 重规划，计数封顶）。
3. **声明式 DAG + 定义感知恢复**（Vibe-Trading 档案 §2/§4）：YAML preset + 拓扑分层调度；resume overlay 两个失效条件（task 定义或 agent spec 变了 / 上游重跑）丢弃已完成结果防 stale summary——部分失败恢复的语义样本。
4. **图上 human 节点回环**（gpt-researcher multi_agents 档案 §2；DataAgent 档案 §5）：interruptBefore 暂停 + checkpoint + updateState(反馈) + stream(null, resumeConfig) 断点续跑——HITL 是图的一等节点而非外挂。

**选型速查**（沿用 A 组「金额 × 可逆性」分轨并扩展到跨组）：

| 财务场景 | 推荐拓扑 | 关键机制来源 |
|---|---|---|
| 月结审查 / 报销初审（多检查项合成一个结论） | T1 层级投票 + 硬规则 clamp | ai-hedge-fund 档案 §2/§5 |
| 报销争议 / 异常调查（需对抗推理） | T2 辩论-裁决（固定轮次可预算） | TradingAgents 档案 §2 |
| 付款建议 / 高金额终审 | T3 并行研究 + 独立审查 + mandate | Vibe-Trading 档案 §2/§5 |
| 并行对账 / 多科目取数 / 多凭证核验 | T6 子 agent 扇出（隔离五件套） | DB-GPT 档案 §2、claude-code 档案 §8 |
| 执行流多观察者（执行/审计/风控并行关注） | T5 事件溯源订阅 | OpenHands 档案 §2 |
| 动态任务分解 | ❌ 不用 T4 群聊；改为图编排层受控路由 | 反例 FinRobot 档案 §2；正例 DataAgent 档案 §2.2 |

同一张图内不同分支挂不同拓扑，正是图编排相对固定管线（gpt-researcher 主链）与自由群聊（FinRobot）的优势。**约束①推论**：子 agent 扇出必须带 DB-GPT 式隔离（独立会话 ID + 只读工具面 + 结论压缩回传）；T4 式动态路由若确需，实现为图编排层的受控路由节点（DataAgent 式）而非消息文本协议。

## 专题二：审批与风控——门放哪、谁来做、失败了怎么办

### 2.1 审批门位置光谱（越靠执行端越强）

- **工具前**（cline 档案 §5）：beforeTool hook（可覆盖策略/改输入/阻断）→ ToolPolicy → 审批回调三段管线；宿主回调**实时读最新设置**（防会话启动时策略快照过期——真踩过的坑）。弱点：粒度只到工具级时挡不住参数级风险。
- **命令/API 前**（codex 档案 §5）：ExecPolicyManager 在执行**前**产出 Forbidden/NeedsApproval/Skip 三态（先判后跑，不是跑失败再问）；opencode（档案 §5.4）用 web-tree-sitter 提 bash 命令前缀做内容级 pattern。财务对应物更简单：「调哪个业务 API + 什么参数」天然是结构化 JSON，内容级粒度在 API 场景比 shell 更易做。
- **内容级 + bypass 免疫**（claude-code-sourcemap 档案 §4）：有序求值管线 deny→ask→工具自评→**内容级 ask 规则（连 bypassPermissions 也要问）**→safetyCheck（敏感路径自动放行阻断）→mode→allow——硬合规位放在任何提权模式之前，DecisionReason 全链可解释。
- **执行出口**（Vibe-Trading 档案 §5；OpenHands 档案 §5）：Vibe 的 LiveOrderGuardTool 是 WRITE 类工具唯一包装，每次 execute 跑 fail-closed 检查链（授权有效→kill switch→持仓对账→纯函数三态裁决）；OpenHands runtime 执行侧二次校验（AWAITING_CONFIRMATION 的动作拒绝执行）——纵深防御，controller/中间层缺位时出口仍守住。

### 2.2 授权不可达（structural guarantee）

Vibe-Trading 档案 §5 的「命门不变量」：授权写入唯一路径 `commit_mandate` **不是工具、不进 agent 工具注册表、不可被自省发现**，只能从 API + 人工 consent_ack 进入；agent 侧只有 `propose_mandate_profiles`（持久化不授予任何权限）。被劫持/幻觉的模型物理上无法自我授权。配套：mandate 默认 30 天强制过期（「live mandate 不许永生」）、frozen dataclass 零验证面（不给 agent 留解析空间）、资金天花板由券商侧专用账户物理执行。迁移要点：财务系统「调额/解冻/白名单维护」的写入口只放审批服务 API（带人工确认回执），agent 面上只有 propose 类工具——比任何 prompt 约束强的结构性保证。

### 2.3 审批外化 API（约束①的服务化答案）

三个先例的共同结构：**审批请求是可重放的事件而非一次性 RPC**；执行端挂起等待（Java 对应 CompletableFuture/阻塞队列）；回复三元语义 once/always/reject(+message)，reject 的 message 回喂模型成为纠错信号（opencode CorrectedError）；always 产生规则副作用并批量解锁同类 pending；断线/无人在线不丢单不隐式作答。
- **opencode**（档案 §5.3）：REST 建请求 / 跨会话待审总表（`GET /api/permission/request`，审批工作台入口）/ reply + SSE `permission.v2.asked/replied` 推送——审批人与执行机物理分离的完整闭环，Spring MVC + SseEmitter 可一比一照抄端点语义。
- **gemini-cli**（档案 §5.5）：确认总线 correlationId 配对 request/response 消息对，a2a-server 桥成 A2A 事件远端代答——TUI 只是总线的又一个订阅者，审批面彻底可插拔。
- **cline**（档案 §5）：hub 层 `approval.requested/respond` 事件协议挂 pendingApprovals map，重订阅即重放 pending（无人在线不丢单）；审批是客户端 capability 声明（不是谁都能答）；另有文件 IPC 第四通道（request/decision JSON 轮询，超时=拒绝）证明通道本身可插拔。
- **图编排关联**（DataAgent 档案 §5）：interruptBefore + checkpoint.nextNodeId 判定 + HTTP 层 `HUMAN_FEEDBACK_REQUIRED` 事件 + 同端点带 threadId resume——纯 REST/SSE 实现 HITL 暂停恢复，但**审批数据必须独立落库**（DataAgent checkpoint 用完即删、审批无痕是反例）。

### 2.4 fail-closed vs fail-open 案例

- **反例**（DB-GPT 档案 §5）：确认门整体包在 `try/except pass` 里——拦截器装配异常**静默放行**；pending 是模块级内存 dict（重启丢失、多副本部署直接失效）；resolve 端点无鉴权（任何能打到 API 的人可替人批准）；且只盖 MCP 连接器，sql_query/代码执行不走门。四缺陷叠加 = 审批门形同虚设。
- **正例**：cline 无回调/回调抛错=拒绝（fail-closed 双保险）+ 非交互会话直接拒；gemini headless 下 ASK_USER 抛错不静默放行（但两处语义不一致是前车之鉴，架构期定死）；OpenHands 未配 analyzer=UNKNOWN=一律询问；Vibe 检查链任何输入不可解析即 DENY、kill switch payload 损坏仍视为触发（fail-closed）。
- **自认权衡**（WrenAI 档案 §5）：planned-SQL 复查 fail-open（注释论证「输出非用户所写、误杀回归>漏放」）——财务场景应改 fail-closed，宁可误杀。
- **分离原则**（Vibe-Trading 档案 §5）：advisory（fail-open、绝不阻塞、默认关）与 mandate gate（fail-closed、唯一权威）严格分离——外部风控建议服务挂了不该阻断合规门，也不能因「建议通过」绕过门。混用会把外部依赖的可用性变成资金/账务链路的可用性风险。

### 2.5 「批准并记住」形态谱系

内存规则（会话级，人人都有）→ 配置落盘（gemini AndSave 写 TOML 串行队列防丢 + **敏感工具强制收窄到 commandPrefix/argsPattern**——防「总是允许整个 shell」；claude-code PermissionUpdate 六操作×五落盘目的地热生效）→ **可审计规则修订**（codex ApprovedExecpolicyAmendment：批准=谁/何时/批了什么前缀，写进策略文件有据可查，且服务端指定客户端可用选项集）→ **内容版本绑定**（cline approvedRevision：被审内容一改即 bump revision 撤销旧审批、与磁盘 spec 对账不一致 fail-closed）→ always 批量解锁（opencode：新规则下符合的 pending 自动放行）+ 级联拒绝（reject 时同会话其余 pending 全拒，防排队放行下一个危险操作）。
迁移要点：财务的「批这版分录 + 以后该供应商 10 万以下自动过」= 可审计规则修订事件（带审批人签名）+ 内容版本绑定，绝不是内存 yes 集合；granular 档关闭某类审批=**自动拒绝而非跳过询问**（codex，防审批疲劳导致人全点同意）；环境级锁死（codex environment.rs：部署档声明 Never 不可被会话覆盖）。

### 2.6 财务 agent 审批架构（跨组拼装）

分层组合，每层来源不同仓：
1. **规则引擎第一道**：gemini 三态 ALLOW/DENY/ASK_USER + 五层优先级带（Admin 层放硬合规 DENY、永远压过用户层），进程内求值——来源：gemini-cli 档案 §5.2。
2. **有序管线 + bypass 免疫位**：超限额/敏感科目判定放在任何提权模式之前，DecisionReason 全链可解释——来源：claude-code-sourcemap 档案 §4。
3. **灰区外化审批**：REST+SSE 审批 API + 断线重放 + reject feedback 回喂模型——来源：opencode/cline/gemini-cli 档案 §5。
4. **执行出口二次校验**：业务 API 调用出口统一再查审批单状态（只执行 CONFIRMED）——来源：OpenHands/Vibe-Trading 档案 §5。
5. **授权不可达 + kill switch 物理制动**：授权写入只在审批服务面（人工 consent_ack）；制动独立于 LLM/主循环/SSE 存活——来源：Vibe-Trading 档案 §5。

整体双轴设计（codex 档案 §5）：审批策略（每步审/按需审/白名单免审/全拒）× 数据访问模式（只读/受限写/全放开）**正交组合**而非一条滑动杆；环境级锁死不可被会话覆盖。

## 专题三：状态与审计——合规审计清单

### 3.1 append-only 事件流（执行审计的地基）

- **OpenHands**（档案 §2/§4）：每事件一 JSON，Observation.cause 回指 Action id（因果链在数据模型层）+ 事件级 llm_metrics/cost；**审批本身也是事件**（待确认动作先入流可展示、批准后以 CONFIRMED 态重发）；压缩决策（Condensation 声明遗忘哪些 event id）回流成事件——压缩可审计。
- **cline**（档案 §4）：canonical 转录 append-only 全保真，compaction 摘要旁挂 `.compaction.json` 且恢复前校验覆盖前缀 hash——「摘要可丢、原文不可变」。
- **codex**（档案 §4）：rollout JSONL 行={timestamp, ordinal, item}，TokenUsageRecord/SecurityRiskScore **单独成持久化项**（成本与安全评分天然入档）；倒序扫描+可寻址读（老会话分页不全量加载）。
- **opencode**（档案 §4.1）：SQLite event(aggregate_id, seq) + 唯一索引 + 会话/消息/part 规范化三表——事务与并发安全优于文件锁，**服务端多会话首选**；JSONL 宜作归档/合规报送格式而非主存。
- 跨组结论：财务 agent 主存直接选 event 表 + 聚合序列唯一索引（Spring Data 可直建）；「审批/成本/风险分/上下文压缩」都应是一等事件类型；摘要永远旁挂可校验、绝不覆盖原文（C 组六仓共识）。

### 3.2 防篡改与时点纪律

- **哈希链账本**（Vibe-Trading 档案 §5）：每笔资金动作 seq + prev_record_hash，append 前验链、断链拒绝追加（LedgerCorruptionError）；**被拒与 halt 也入账**；问责链 mandate_snapshot_ref + consent_record_ref 让每笔动作回溯到授权它的人工点击。财务的资金/记账动作流照抄；跨实例并发语义（本组只有 flock）需自行设计。
- **point-in-time 决策日志**（TradingAgents 档案 §4）：决策当下存 pending（不加 LLM 调用），事实发生（核销/月结完成）后回填 outcome+反思，resolution_date 供历史过滤防「偷看未来」；ai-hedge-fund 的 PIT 快照（市值 latest-only 陷阱是现成案例，档案 §8）同源——「当时知道什么」必须可回答。
- **版本绑定审计**：方法论指纹（Vibe-Trading 档案 §4：prompt/skills/工具注册表 hash → manifest_hash，刻意排除 timestamp/run_id，「两次运行方法论相同则 hash 必须相同」，可 diff 出哪个 skill 变了）+ 图形状签名进 checkpoint key（TradingAgents 档案 §4：改图后旧执行态自动作废）。**审计记录必须绑定产生它的规则与拓扑版本，否则重放无法解释。**

### 3.3 审计的经济性（两条降本设计）

- **审计即缓存**（ai-hedge-fund 档案 §4）：PromptCache 一决定一文件（key=内容哈希），同时是缓存（回测重跑 $0）/审计记录（每个 Signal 背后精确 prompt+response+snapshot_hash）/调试踪迹（解析失败原始响应留盘）三合一——「每个 LLM 决策可回放」的合规要求可零额外成本起步。
- **审计双平面**（SQLBot 档案 §4/§5）：执行面 chat_log（每次 LLM 调用：14 种操作枚举 + 完整 prompt + reasoning + token + 时长）× 管理面 `@system_log` 声明式注解（IP 代理链解析、敏感 header 排除、DELETE 前资源名补录）；再叠 DB-GPT view message（用户最终看到的 SQL+数据+图表类型作为独立消息类型落库，档案 §4）——「AI 决策可回放 + 管理操作可追责 + 用户所见可举证」三线齐备。

### 3.4 redaction 位置（三种合法位置 + 一个反例群）

- **生成侧占位符**（browser-use 档案 §6）：secret 从头到尾不进 LLM 视野（`<secret>` 占位符协议，D 组档案 §2 模式 2）——最强，凭据类首选。
- **持久化适配器写时脱敏**（OpenHands 档案 §4）：`_replace_secrets` 在入存储前统一替换——集中一处，不靠各工具自查。
- **进 sink 前脱敏**（Vibe-Trading 档案 §5）：redaction 在进任何审计 sink 之前执行（broker 响应里的 token/PII），与 trace/audit/公开 metadata 三路共用。
- **反例群**（B 组档案 §4）：db_pwd 明文入库且 API 原样回传、硬编码 key + AES-ECB「装饰性加密」、明文入库但表注释宣称「加密存储」——「有加密≠加密有效」，评审看密钥管理（KMS/env、AEAD-GCM），不看是否调了加密函数。

### 3.5 合规审计清单（跨组汇总，可直接当设计 checklist）

1. 会话 = append-only 事件流（含审批/成本/风险分/压缩事件），主存事件表 + 聚合序列唯一索引（opencode 档案 §4.1）。
2. 每个用户可见产物独立落库——view message（DB-GPT 档案 §4）。
3. 资金/记账动作流加哈希链（断链拒写）+ 问责链回溯到人工授权（Vibe-Trading 档案 §5）。
4. LLM 决策缓存即审计：prompt/response/输入快照哈希按内容寻址落盘（ai-hedge-fund 档案 §4）。
5. 决策日志 pending→resolved 带 resolution_date，支持时点过滤（TradingAgents 档案 §4）。
6. 规则与拓扑版本进审计键：manifest 指纹 / 图形状签名（Vibe-Trading 档案 §4、TradingAgents 档案 §4）。
7. 凭据全程占位符或写时脱敏，密钥在代码与数据之外（browser-use/OpenHands 档案 §4/§6）。
8. 审批数据（谁/何时/批了什么版本/理由）独立持久化表（DataAgent checkpoint 即删是反例，档案 §5）。
9. 回滚不破坏现场：revert 两阶段 stage→确认→commit、可反悔（opencode 档案 §4.2）；checkpoint 恢复前先 stash 现状（cline 档案 §4）。
10. 不可逆动作崩溃恢复 = 对账不重发：动作前写 crash-safe 副作用标记，重启后拿对端证据关闭重发窗口，mutation 永不自动重试（Vibe-Trading 档案 §5）。
11. 审计双平面：执行面逐 LLM 调用留痕 × 管理面声明式操作日志（SQLBot 档案 §4/§5）。
12. 决策失败可见化：不可解析输出返回哨兵值（REVIEW）进人工队列，绝不静默降级（TradingAgents 档案 §5）。

## 专题四：工具与系统集成——单源真相、凭据谱系、读写隔离、MCP

### 4.1 工具注册与权限单源真相（一份声明多处消费）

- **codex**（档案 §5/§6）：FileSystemSandboxPolicy 同一份 entries **双处执行**（进程内文件工具 + OS 沙箱系统调用层），deny glob fail-closed——单源真相防两套权限漂移（该思路独立于沙箱也成立：一份资源声明同时驱动应用层鉴权与基础设施 grant）。
- **DB-GPT**（档案 §5/§6）：catalog.json 的 confirm_actions/read_actions **三处消费**（确认拦截器、子 agent 只读过滤、确认弹窗参数打码）——「哪些动作是写」是目录数据不是代码分支。同步记住其三缺陷的修法：确认状态入持久层、拦截 fail-closed、resolve 带操作者身份与审计记录。
- **WrenAI**（档案 §2）工具面四分法：上下文检索 / dry-plan 校验 / 受治理执行 / 记忆写回各自成工具，按能力开关裁剪（memory 关→记忆工具自动消失）；browser-use（档案 §6）动作 schema 联合注册 + 装饰器注入执行上下文——工具面按场景动态收缩的两个范本。
- 迁移要点：Java 侧建「工具目录 = 注册中心 + 读写权限声明 + 审计元数据」三合一单源（Spring Bean + 注解 + 配置库），审批门、子 agent 工具过滤、工具列表动态裁剪（对 LLM 隐藏）、审计打点四处消费同一份声明；deny 的工具从发给模型的工具列表**移除**（opencode 档案 §5.1）。

### 4.2 凭据管理谱系（六级链，两端都是教训）

**明文入库**（DB-GPT db_pwd 且 API 原样回传；DataAgent 明文+表注释宣称「加密存储」）→ **弱加密**（SQLBot 硬编码 key `SQLBot1234567890` + AES-ECB；supersonic 同为 AES-ECB——源码即密钥，装饰性加密）→ **env 变量**（多数仓底线；WrenAI `${VAR}` 占位 + .env 解析 + 「永不在聊天里要凭据」写进编排模板）→ **对称加密 + env 密钥**（DB-GPT Fernet CredentialStore：master key 走 env、确认弹窗敏感参数打码、`${env:VAR}` 参数插值）→ **六级解析链 + 本地 vault**（data-formulator TokenStore：cached→refresh→sso_exchange→delegated→vault，admin-pinned 与 user-owned 连接器分离，删除连接器同步清 vault）→ **secret 占位符协议**（browser-use：LLM 全程只见键名，工具执行层域限定替换）。
迁移要点：企业侧取谱系右端与中端的组合——「vault/KMS 存真值 + 引用键在配置与消息中流转 + 工具执行层域限定解析 + 展示层全量打码」；评审要点永远是密钥管理而非「有没有调加密函数」。

### 4.3 读写隔离（四层递进 + 出口二次校验）

- **AST 校验层**（B 组档案 §4 已给六层组合最优解，此处只列跨组补充）：sqlglot（SQLBot/WrenAI）、Druid（DataAgent）、tree-sitter（opencode/claude-code）——「内容级粒度是否上语法树」是命令/SQL 安全的分水岭；财务 API 场景的参数级白名单同理。
- **执行边界 AOP**（supersonic 档案 §5）：`@S2DataPermission` 切面强制注入行权限 WHERE（jsqlparser）+ 列敏感级校验（sensitiveLevel=HIGH 须授权）+ **QueryAuthorization 透明回执**（告知用户结果已过滤及条件）——Java 可直接照抄；「过滤行为对用户可解释」可直接进合规报告。
- **语义方言边界**（supersonic S2SQL / WrenAI manifest 表封闭 + RLAC 缺 session property 规划直接失败）：LLM 只写逻辑层（指标名/模型名），物理展开在确定性翻译层——「LLM 输出落在可校验的受限表达域」是 B 组谱系结论的分水岭；财务取数走此路（口径文件进 Git 走 PR 后发布运行时）。
- **工具面分级**（data-formulator 档案 §2.1/§2.5）：inspection（并行、无副作用、不示用户）vs action（串行、用户可见、**一动作一回合由 shell 强制**）；SPJQ 受限计划 + 人工选择状态机（AWAITING_SELECTION）与自由探索双轨——「查账随便查、记账/付款逐笔提交」的直接对应。
- **出口分类**（Vibe-Trading 档案 §5）：读写三级分类 default-deny——不可信服务自述（readOnlyHint）只能降级不能升级、维护者 curated map 优先、UNKNOWN 一律按写走门。

### 4.4 MCP 集成形态（三个方向）

- **作为 client 的治理**：Vibe-Trading（档案 §5/§6）券商 MCP 工具运行时发现 + 读写三级分类（annotation 只能降级、curated map 反制「谎称 readOnlyHint 的 place_order」）；codex（档案 §6）EnvironmentMcpPolicy 按 server 的 command/URL 强制或限制（环境级管控，企业托管）；gemini-cli（档案 §6）多源配置合并「includeTools 取交集、excludeTools 取并集——最严者胜」。共同纪律：**MCP server 自述的 readOnlyHint 不可作安全依据**（MCP 规范自己的警告）。
- **作为 server 的双暴露**：DataAgent（档案 §6.5）同一服务 REST/SSE + MCP Server 双暴露（`nl2sql` 全图模式工具化，供 Claude Desktop 等消费）——「agent 服务被别的 agent 系统集成」的最低成本路径；SQLBot/WrenAI/gpt-researcher/Vibe 同构。约束①下这是推荐形态：业务侧消费 REST 主面，其他 agent 系统消费 MCP 工具面。
- **检索器式集成**（gpt-researcher 档案 §6）：MCP 作为数据源 provider 之一 + fast/deep/disabled 执行策略分档——把 MCP 工具纳入统一成本-精度分档，而非特权通道。

### 4.5 财务业务系统集成建议（约束①落地形态）

1. **工具面 = 业务 API 受控封装**：不提供 shell/任意代码执行工具；executor 注入接缝（cline 档案 §6）+「能力面收窄优先于沙箱」（C 组档案 §5 结论）；确需分析代码（对账脚本/批量核算）才上容器隔离——OpenHands 每会话容器 + 容器内执行服务器 + session key 是 JVM 生态最可平移形态（JVM 无 OS 沙箱等价物，SecurityManager 已废弃）。
2. **工具目录单源真相**（4.1）：注册、权限声明、审计元数据一处维护、多处消费。
3. **凭据走引用协议**（4.2）：业务系统凭据不进 agent 配置库、不进 prompt、不进任何展示层。
4. **读写语义双端校验**：工具目录声明 + 业务 API 网关侧复核；外部风控建议（advisory，fail-open）与硬门（fail-closed）分离（Vibe-Trading 档案 §5）。
5. **语义层口径文件进 Git 走 PR 审批后发布运行时**（B 组结论沿用：机制学 supersonic、治理形态学 WrenAI）。
6. **egress 白名单只通业务网关**：codex「网络按域名审批」的服务端等价——agent 进程无公网 outbound，一切外部调用经统一 API client 层（codex 档案 §5、C 组档案 §5）。
7. **对业务侧暴露双面**：REST/SSE 主面 + MCP 工具面（4.4，DataAgent 档案 §6.5）。
