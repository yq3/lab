# 04 权限审批与凭据的持久化（codex / opencode / gemini-cli / claude-code / DB-GPT / data-formulator / browser-use / Vibe-Trading）

> agent-persistence 轮第 4 路。基线：codex@ee6814bfa4 · opencode@95daf90670 · gemini-cli@9c1b0a6105 · claude-code-sourcemap@a8a678cb62（【还原源码】）· DB-GPT@04559f9ccf · data-formulator@5477f0e236 · browser-use@50f205533 · Vibe-Trading@f84b2977a5。审批流程结论见 agent-oss 轮档案，本文不复述，只补「存成什么、写到哪、什么格式」。
>
> **综述**：八仓在「规则 / 待审单 / 凭据」三类状态上呈现出清晰的存储谱系——①**授权规则**从内存 Map（人人都有）演进到结构化文件（gemini TOML 五层带 / claude settings JSON 多源 / codex Starlark `.rules` 追加式修订）再到数据库表（opencode `permission` 表三元组）；②**待审单**几乎全员内存（opencode Deferred Map / DB-GPT 模块级 dict / codex ApprovalStore），重启即丢是通病，唯一例外是把审批请求做成可重放事件（cline hub / OpenHands 事件流，非本轮对象）；③**凭据**从明文列到 Fernet+env key 到本地 SQLite vault 到「占位符不进模型」协议。

**AndSave 落盘**：写到 `auto-saved.toml`（storage.ts:28）——workspace 可信且开启 workspace policies 时写 `<project>/.gemini/policies/auto-saved.toml`，否则写 `~/.gemini/policies/auto-saved.toml`（storage.ts:240-249；scheduler/policy.ts:130-156 决定 persistScope）。实现全在 `createPolicyUpdater`（config.ts:712-934）：

- **串行队列**：`let persistenceQueue = Promise.resolve()`（L718），每次持久化 `persistenceQueue = persistenceQueue.then(async …)`（L796）——Promise 链式排队防并发丢更新。

落盘规则形态（`[[rule]]` 数组项）：`{decision:'allow', priority:950, toolName, mcpName?, commandPrefix?|argsPattern?, allowRedirection?, modes?}`（TomlRule config.ts:646-657）。

### A3. codex：Starlark 规则文件 + 追加式修订【核心】

**规则文件路径与加载**：用户层 `$CODEX_HOME/rules/default.rules`（`default_policy_path` core/src/exec_policy.rs:867；常量 L54-56）。加载是**多层合并**：config 各层（package→admin→system→cloud→user→profile→cwd→tree→repo→runtime）的 `<config_folder>/rules/*.rules` 按低→高收集，高优先层覆盖低层（`load_exec_policy` exec_policy.rs:662-716）；最后叠加 requirements 层 overlay（`merge_overlay` execpolicy/src/policy.rs:178-202）。

**一条规则的完整结构**（Starlark 方言，builtins 在 execpolicy/src/parser.rs:347-472）：

```python
prefix_rule(pattern=["cargo", "test"], decision="allow",
            match=["cargo test --lib"], not_match=["cargo test --release"],
            justification="CI 快速验证")
network_rule(host="api.github.com", protocol="https", decision="allow",
             justification="...")
host_executable(name="python", paths=["/usr/bin/python3"])
```

- `decision ∈ allow/prompt/forbidden`（parser.rs:357-359）；pattern 元素支持 alternation：`["git", ["pull","push"]]` 展开为多条 PrefixRule（parser.rs:390-403）。
- `match/not_match` 示例在**解析期即验证**规则确实匹配/不匹配（PendingExampleValidation，parser.rs:117-152）——规则文件自带可执行测试。
- 内存结构 `Policy { rules_by_program: MultiMap<String, RuleRef>, network_rules: Vec<NetworkRule>, host_executables_by_name }`（policy.rs:27-32）。

**ApprovedExecpolicyAmendment 批准后怎么写回**（`append_amendment_and_update` exec_policy.rs:464-512）：**纯追加、非修订记录**——`spawn_blocking` 调 `blocking_append_allow_prefix_rule`（execpolicy/src/amend.rs:65-81）把 `prefix_rule(pattern=["cargo","test"], decision="allow")` 作为**新行 append 到 default.rules**：advisory flock 独占锁、与现有行全等则跳过去重、末尾无换行先补（amend.rs:147-193）。随后内存侧 clone + `add_prefix_rule` + ArcSwap `policy.store(Arc::new(updated))` 热生效（exec_policy.rs:508-511）。⚠️ **规则文件本身不记录批准人/时间**——可审计性全靠 rollout 事件流。

**ApprovedForSession 缓存在内存**：`ApprovalStore { map: HashMap<String, ReviewDecision> }`（core/src/tools/sandboxing.rs:40-42），经 `services.tool_approvals`（Mutex）读写；MCP 侧同款（mcp_tool_call.rs:2108-2113）。不写 rollout、重启即失。

**环境锁（deployment Never）存哪**：不是文件哨兵而是 **requirements 约束对象**——`ConfigRequirements.approval_policy: ConstrainedWithSource<AskForApproval>`（config/src/config_requirements.rs:175），允许集合由 requirements 层锁定，来源枚举 `RequirementSource`（L44-62）：MDM managed preferences / 企业云下发层 / 系统文件 `/etc/codex/requirements.toml`（Unix）或 `%ProgramData%\OpenAI\Codex\requirements.toml`（Win）等（loader/mod.rs:100-127）。会话想设 `Never` 时 `can_set()` 检查失败即拒绝（config_requirements.rs:3579-3637）。

### A4. opencode：v2 saved 表 + 两代内存规则【核心】

**v2 saved 持久授权表 DDL**（drizzle，core/src/permission/sql.ts:7-20，抽查复核命中 :15-19）：

```sql
CREATE TABLE permission (
  id         TEXT PRIMARY KEY,            -- 'psv_' + 单调序列
  project_id TEXT NOT NULL REFERENCES project(id) ON DELETE CASCADE,
  action     TEXT NOT NULL,
  resource   TEXT NOT NULL,
  created_at / updated_at,
  UNIQUE (project_id, action, resource)
);
```

模型 `PermissionSaved.Info = {id, projectID, action, resource}`（schema/src/permission-saved.ts:14-19）；`add` 按资源展开多行 + `onConflictDoNothing` 幂等（core/src/permission/saved.ts:54-69）。**effect 不入库**——读回时恒映射 `{action, resource, effect: "allow"}`（core/src/permission.ts:131-135 savedRules）。四元组的实相：`Request = {id, sessionID, action, resources[], save?, metadata?, source?{type:'tool', messageID, callID}}`（schema/src/permission.ts:25-38）——**save[]（要记住的 patterns）与 source（来源回溯）只活在请求/事件对象里，持久层收敛为 (project, action, resource) 三元组**。

**会话内内存规则**：v2 pending 为 `Map<ID, {request, agent?, deferred}>`（core/src/permission.ts:103-107, L117），实例 finalizer 全量 DeclinedError（L119-129）；always+save → `saved.add` + 用新 savedRules 重评其余 pending 批量解锁（L250-283）。v1 是 `State { pending: Map<ID, PendingEntry>, approved: PermissionV1.Rule[] }`（opencode/src/permission/index.ts:23-26）；v1 session 级 ruleset 是 session 记录字段 `permission: PermissionV1.Ruleset`（schema/src/v1/session.ts:566），随 v1 会话 JSON 持久化。

**事件形态**：`permission.v2.asked`（data = Request 全字段）/ `permission.v2.replied`（`{sessionID, requestID, reply: once|always|reject}`）（schema/src/permission.ts:43-52）。⚠️ 两代都**不在 durable manifest**（durable-event-manifest.ts 只收 Session 类事件）→ 只走进程内 PubSub/SSE 推送，**不写 event 表**。

### B5. DB-GPT：模块级内存 dict（反例证据）【核心】

### B6. opencode 跨会话待审总表：也是内存

`GET /api/permission/request` 的数据源是 `PermissionV2.list()` = `Array.from(pending.values())`——**location 级内存 Map，不是查库**（core/src/permission.ts:288-290）。审批工作台语义成立的前提是 server 进程活着；重启后 pending 全部随 finalizer 置拒（L119-129）。审计回看则依赖 SSE 订阅者自己存事件（事件本身不落库）。⚠️ 即「审批面外化」做全了，「待审单持久化」没做——与 cline hub 的断线重放（pendingApprovals 重订阅重放）相比是明确缺口。

### C10. Vibe-Trading：mandate/consent 双文件 + 文件哨兵 kill switch【核心】

**mandate 存储形态**：frozen dataclass（Mandate/HardCaps/UniverseConstraint/ConsentMeta，live/mandate/model.py）在内存零验证面；**落盘为 JSON 文档** `<runtime_root>/live/<broker>/mandate.json`（runtime_root 缺省 `~/.vibe-trading`，live/paths.py:3-12；store.py:39,58），0600 权限、tmp+replace 原子写（commit.py#_atomic_write_json L167-187）。文档字段（commit.py:488-503）：`{schema_version, mandate_id, hard_caps{...}, universe{...}, flatten_on_halt, consent{created_at, consent_token_sha256, broker, account_ref, expires_at}}`。读侧 `load_mandate` 严格 fail-closed：文件缺失/malformed/结构无效/schema_version 不识 → None → 执行门全拒（store.py:42-70）。**写入顺序硬编码"证据先于授权"**：先写 consent record 再写 mandate（L520-524 注释：consent 写失败则 mandate 不可用；mandate 写失败的孤儿 consent 无害且利于审计）。

**consent 记录（人工授权回执）**：`<runtime_root>/live/<broker>/consent/<cr_*.json>`（commit.py:162-164, L523），字段 `{consent_record_id, mandate_id, proposal_id, selected_ordinal, adjustments, consent_ack: true, session_id, broker, account_ref, resolved_profile, flatten_on_halt, ceilings_ref, created_at, expires_at}`（L504-519）。`consent_token_sha256 = sha256("proposal_id|ordinal|cr_id|created_iso")` 绑定到 mandate 文档（L485-486）——每笔实盘单可回溯到授权它的人工点击。前置 proposal 存 `<broker>/proposals/mp_<32hex>.json`（id 正则约束防路径注入，L189-196），一次性消费（`_invalidate_proposal` L527）。

**kill switch 独立存储标志位**：文件哨兵 `<runtime_root>/live/HALT`（全局）+ `<runtime_root>/live/<broker>/HALT`（单券商）（halt.py:40-69，抽查复核命中）。payload = JSON `{tripped_at, by: cli|frontend|file, reason}`，trip 走 tmp+replace 原子写（L72-108）。**判读实现**：`halt_flag_set` 是纯文件存在性检查——不查 LLM、不查进程内 flag（L135-163）；全局哨兵存在则对任何 broker 返回 True；**损坏/空 JSON 仍视为 tripped**（`read_halt` 对 unreadable/malformed 返回 `{}`，存在性才是权威，payload 只是归因元数据，L165-176）；**非法 broker key 也 fail-closed 返回 True**（L159-163）。清除 = 删文件（clear_halt L111-131）。

## 设计结论（≤5）

1. **持久授权的最小完备 schema 是 (scope, action, resource) 唯一索引 + effect 隐含 allow**（opencode `permission` 表）：save/source 等审批时上下文留在事件流里，规则表保持极简，INSERT ON CONFLICT 天然幂等——一张表 + 唯一约束即可抄。
2. **「批准并记住」写文件必须带三件套：串行队列 / 原子写 / 损坏恢复**（gemini `createPolicyUpdater`：Promise 链 + tmp(wx)+rename + .bak），且落盘规则与内存规则共用同一优先级分数防双轨语义漂移。codex 的 append-only + flock 是 DSL 文件的对应答案，但**规则文件不记批准人是缺陷，审计必须另有事件流**——财务场景规则修订表应带 (批准人, 时间, 前缀, consent 引用) 四列。
3. **待审单持久化是全员缺口**：opencode/DB-GPT 的 pending 都在内存、重启即丢；服务端审批工作台要成立，待审单必须与审批事件一样入库存档（且 resolve 要带操作者鉴权——DB-GPT 三缺陷是完整反面清单：内存 dict + fail-open try/pass + 无鉴权 resolve）。
4. **凭据最优组合已在谱系右端拼好**：vault/KMS 存真值（data-formulator 的 SQLite+独立 key 文件是最小实现）+ 引用键在配置与消息中流转（browser-use 域限定替换）+ 表单/弹窗全量打码（DB-GPT `_summarize_args` 的 HIDDEN 键集合）+ 删除时 session 与 vault 成对清理。
5. **授权与制动的存储要用"文件存在性 + 证据先于授权"两个物理约定**（Vibe-Trading）：kill switch 只认哨兵文件存在、payload 损坏仍触发（fail-closed 判读收口在一处）；mandate 写入先落 consent 回执再落授权文档，consent_token_sha256 把两者绑死——比任何数据库标志位都更难被进程内代码（含被劫持的 agent）篡改或绕过。
