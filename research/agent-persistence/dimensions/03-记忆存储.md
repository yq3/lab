## 1. TradingAgents：单文件 append-only markdown

**介质与格式**【核心】

- 落点：`$TRADINGAGENTS_HOME/memory/trading_memory.md`（`default_config.py:76`，env `TRADINGAGENTS_MEMORY_LOG_PATH` 可覆盖）。
- 条目分隔符原文：`"\n\n<!-- ENTRY_END -->\n\n"`（memory.py:13，注释明说选 HTML 注释因为不会出现在 LLM prose 输出里，是安全硬分隔符；抽查复核命中）。
- pending 条目：首行 tag `[trade_date | ticker | rating | pending]` + 空行 + `DECISION:\n{全文}`（store_decision，:30-49）。
- resolved 条目 tag 七段：`[date | ticker | rating | raw% | alpha% | {N}d | resolved:YYYY-MM-DD]`（`_resolved_tag` :233-246；百分比 `+.1%` 格式），后接 DECISION 与新增 `REFLECTION:\n{反思}` 段。`resolution_date` 来自收益计算所用最后一根价格棒的日期：`stock.index[holding_days].strftime("%Y-%m-%d")`（trading_graph.py:317）——它是 point-in-time 过滤的截断点（#1251 防回测偷看未来）。
- 解析：`_parse_entry` 按 `|` 切 tag（≥4 字段才认），`resolved:` 前缀从第 7 段起扫描（:285-316）。

**写入路径**：propagate 结束 append pending，写前做幂等防重——逐行原始文本扫描 `[date | ticker |` 前缀 + `| pending]` 后缀（:40-44，刻意不走全量解析）。Phase B 批量更新：整文件 split 分隔符 → 内存改写 → **temp 文件（`.tmp` 后缀）+ `tmp_path.replace(self._log_path)` 原子替换**（batch_update_with_outcomes :226-229；单条版同构 :173-175）。

**检索路径**：`get_past_context` 全量 load 后倒序取同 ticker 5 条（全文）+ 跨 ticker 3 条（仅 REFLECTION，DECISION 截 300 字符）；`as_of` 过滤 `resolved <= as_of`（:82-84）。无索引无向量。

**清理与遗忘**：`memory_log_max_entries`（默认 `None`=不轮转，default_config.py:80）。轮转只数 resolved 条数、超限从最旧开始丢 resolved，**pending 永不删**（"they represent unprocessed work"，`_apply_rotation` :248-283）。

**写入与并发**：`add()` 30 秒滑动窗口 sha256 去重（:32,457-470）；写路径全程 `fcntl.flock`（`.lock` 文件，5s 超时降级 best-effort，Windows no-op，:41-72）；正文清洗控制字符 + 8000 字符截断（:23-24）。

**检索**：FTS5 rank × importance 加权（`-rank × (0.5+0.5×importance)`，:403-406）→ 失败降级 token 交集扫描（metadata/keywords ×2.0 权重）→ semantic_links 结果补位填满 max_results（:435-453）。首次空结果自动全量重建索引一次（:376-386）。无向量。

## 3. crewAI：LanceDB 单表文档模型

**介质与格式**【核心】`lib/crewai/src/crewai/memory/storage/lancedb_storage.py`

- 落点：`$CREWAI_STORAGE_DIR/memory` 或平台数据目录（:67-74）；连接 `lancedb.connect(path)`，**单表 `memories`**（:48）。
- 行 schema（placeholder 建表 :160-181，`_record_to_row` :247-262）：`id(uuid4)/content/scope(层级路径，默认 "/")/categories_str(json.dumps)/metadata_str(json.dumps)/importance(float 0-1)/created_at/last_accessed(isoformat)/source/private(bool)/vector`。注意 **categories/metadata 是 JSON 字符串列**，importance/scope 是一等列。
- 向量维度：默认 **3072**（对齐 text-embedding-3-large，`DEFAULT_VECTOR_DIM=3072` :27）；无 embedding 时写零向量占位（:172）。建表用「placeholder 行 + 立即 delete」的取巧方式（:176-180）。
- 索引：scope 列 **BTREE 标量索引**（:183-199）；后台 compaction：每 100 次 save 或开表时 `table.optimize()`（daemon 线程，:50,201-231）；写冲突（"Commit conflict"）指数退避重试 5 次（:34-39,128-153）；跨进程用 `crewai_core.lock_store` 命名锁 `lancedb:{abs_path}`（:92）。

**embedding 配置**：`Memory.embedder` 接受 callable / provider dict / None；None 时 `build_embedder({"provider":"openai"})`（unified_memory.py:52-55,96）；MemoryRecord 里 embedding 字段 `exclude=True` 不参与序列化省 token（types.py:48-51）。

**写入（consolidation 后记录怎么变）**：encoding_flow.py `execute_plans`（:341-505）——LLM 相似度 ≥0.85 的 plan 去重后：**delete** 旧 record_id 集合；**update** = 保留原 id/scope/categories/metadata/importance/created_at，换 `content=new_content`、`last_accessed=now`、**批量重嵌入**换 vector（:455-466）；**insert** 新 MemoryRecord（caller 字段 > LLM 抽取字段优先级，:313-331）。即合并结果 = 旧条目原地改写内容+向量，不保留合并前版本。

**检索**：RecallFlow（LLM 子查询×scope 并行）→ 复合评分（semantic 0.5 / recency 0.3 权重、30 天半衰期，types.py:366-368 已在框架轮核验）。**遗忘**：无 forget API；CLI `crewai reset-memories --memory/--knowledge/--agent-knowledge/--kickoff-outputs/--all`（utilities/reset_memories.py:63-140）；memory 重置 = 整表 drop_table（lancedb_storage.py:603-610）；带 scope_prefix 时用字符串区间删除 `scope >= 'p' AND scope < 'p/\uffff'`。

## 4. langgraph：BaseStore 文档模型与 pgvector 双表

**文档模型**【核心】`libs/checkpoint/langgraph/store/base/__init__.py`：Item = `namespace(tuple[str,...] 层级路径) + key(命名空间内唯一) + value(JSON dict) + created_at/updated_at + score(检索附加)`（:119-149）；PutOp(value=None 即 delete，:935-939）。

**put(index=) 的字段索引存储**：`index` 参数控制字段级索引（None=用 store 配置的 fields；False=禁用；list[str]=本条目字段路径，支持嵌套 `metadata.title`/数组 `chapters[*].content`/下标 `authors[0].name`，:851-875）。**不是 doc 内向量列，而是独立向量表按 (doc, field) 一行**：

**PostgresStore DDL**（libs/checkpoint-postgres/.../store/postgres/base.py:63-145）：

```sql
CREATE TABLE store (
    prefix text NOT NULL,          -- namespace 的 '.' 连接表示
    key text NOT NULL,
    value jsonb NOT NULL,
    created_at/updated_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP,
    expires_at TIMESTAMPTZ, ttl_minutes INT,   -- 迁移3追加：TTL
    PRIMARY KEY (prefix, key)
);
CREATE INDEX store_prefix_idx ON store USING btree (prefix text_pattern_ops);
CREATE INDEX idx_store_expires_at ON store (expires_at) WHERE expires_at IS NOT NULL;

CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE store_vectors (
    prefix text, key text, field_name text,
    embedding vector(dims)|halfvec(dims),
    created_at/updated_at TIMESTAMPTZ,
    PRIMARY KEY (prefix, key, field_name),
    FOREIGN KEY (prefix, key) REFERENCES store(prefix, key) ON DELETE CASCADE
);
CREATE INDEX store_vectors_embedding_idx ON store_vectors USING hnsw|ivfflat (embedding ops) [WITH(...)];
```

**search 过滤+向量组合**（base.py:440-615）：filter 编译为 `value->%s = %s::jsonb`（等值）或 `value->>%s > ...`（$gt/$gte/$lt/$lte/$ne，:647-667）；有 query 时：join store_vectors 的 CTE（距离算子 `<->` l2 / `<=>` cosine，cosine 得分 `1-neg_score`，:1442-1450），`DISTINCT ON (prefix,key)` 取同文档多字段最佳分再 `ORDER BY score DESC LIMIT/OFFSET`，limit 预放大 `limit×每文档向量数×2+1`（:508-510）；无 query 退化为 `ORDER BY updated_at DESC`。TTL：get/search 命中可顺带续期（refresh_ttl 包装 UPDATE，:566-580）。ANN 可配 hnsw(m,ef_construction)/ivfflat(nlist)/flat、vector/halfvec、l2/inner_product/cosine（:178-233）。

**InMemoryStore 对应结构**（store/memory/__init__.py:186-189）：`_data: dict[namespace, dict[key, Item]]` + `_vectors: dict[namespace, dict[key, dict[field_name, list[float]]]]`——与 store/store_vectors 两表严格同构。

**CompositeBackend 路由**（backends/composite.py:228-280）：构造参数 `routes: dict[prefix, BackendProtocol]`（如 `{"/memories/": StoreBackend(...), "/cache/": ...}`），按 **前缀长度降序** 匹配（`sorted_routes`），未命中走 default（典型 StateBackend=thread 内）；glob/grep 模式会被改写去前缀再下发（`_strip_route_from_pattern` :60-90）。

**StoreBackend 落点**（backends/store.py）：`/memories/note.md` → `store.put(namespace, "note.md"(去前缀 key), value)`（write :428-447）；value dict = `{content: str, encoding: "utf-8", created_at?, modified_at?}`；兼容 legacy `list[str]` 行拼接（:190-196）。namespace 由 factory 从 Runtime 生成（如 `(user.identity, "filesystem")`），字符白名单校验防 glob 注入（:46-87）。**即：模型 edit_file 写 `/memories/**` 最终落到 langgraph BaseStore（跨 thread 持久），写其他路径落 thread state（随 checkpoint）。**

## 6. agentscope：memory.md + frontmatter + LLM 选择器检索

**介质与格式**【核心】`src/agentscope/middleware/_longterm_memory/_agentic_memory/_middleware.py`：`{workdir}/{memory_dir="Memory"}/` 下 topic 文件 + `MEMORY.md` 索引（幂等创建空文件，:803-821）。

- frontmatter 字段仅 3 个：**`name` / `description` / `type(user|feedback|project|reference)`**（模板 :223-234）；description 被明确定义为「检索触发器」而非摘要——要写成"当你即将 X 时先 Read 本文件"（:250-267）。
- MEMORY.md 索引行格式 `- [Title](file.md) — one-line hook`，**是索引不是记忆**，>200 行截断（:236-242）；系统提示注入预算 `memory_max_tokens=4000`，超限截断并附 `<system-reminder>` 提示用 Read+offset 续读（:534-550）。
- frontmatter 解析是自研正则（仅标量 key:value，无嵌套，:862-889）；扫描每文件只读头部 ~256 token 等价字节（:928-937）。

**检索实现**（:709-801）：**不是 grep 也不是向量，是 LLM 结构化选择**——① 扫全部 topic 文件 frontmatter 头 → ② 拼 manifest `- [type] filename (YYYY-MM-DD): description`（:683-707）→ ③ `generate_structured_output(_MemorySelection)`（selected_files ≤5）→ ④ **幻觉文件名过滤**（`f in valid_filenames`，:757-759）→ ⑤ 读选中文件（每文件截 2000 token）以 HintBlock 注入 reasoning 循环（:666-674）。异步执行：on_reply 起 task、on_reasoning 轮询消费恰好一次。另有兜底：提示词教模型自己 `Grep path={memory_dir} glob="*.md"`（:324-330）。写入完全由模型用 Write 工具自主完成。

**与 Mem0/ReMe 存储介质差异**（`_mem0/`、`_reme/`）：Mem0Middleware 走 mem0 `AsyncMemory`，存储由 mem0 MemoryConfig 决定（`vector_store`/`history_db_path`/`reranker` 透传，_mem0/_agentscope_adapter.py:341-346）⚠️ 接口透传推断；ReMeMiddleware 用 ReMe 内嵌配置（backend=base + dream_extract/integrate/topics/finish 四步「夜间 dream」巩固管线）。即：Agentic=纯 markdown 文件、Mem0=mem0 托管（向量库+SQLite 历史）、ReMe=内嵌 ReMe 服务自有存储，三者介质完全不同、中间件接口统一。

## 7. supersonic：MySQL 表 + langchain4j 向量库双写

**DDL**【核心】（launchers/standalone/src/main/resources/db/schema-postgres.sql；DO 映射 `ChatMemoryDO.java`，表名 `s2_chat_memory`）：

```sql
CREATE TABLE s2_chat_memory (
    id SERIAL PRIMARY KEY,
    question varchar(655), side_info TEXT, query_id bigint, agent_id INTEGER,
    db_schema TEXT, s2_sql TEXT,
    status varchar(20),                 -- PENDING/ENABLED/DISABLED
    llm_review varchar(20), llm_comment TEXT,      -- LLM 评审结果/意见
    human_review varchar(20), human_comment TEXT,  -- 人工终审结果/意见
    created_at/updated_at TIMESTAMP, created_by/updated_by varchar(100)
);
```

（MySQL/H2 变体同构；无独立向量列——**向量在库外**。）

**向量库同步时机**（`MemoryServiceImpl.java`）：
- **写入 MySQL**：SqlExecutor 查询成功后 `createMemory`（executor/SqlExecutor.java:52），同 agent 同 question 且 ENABLED 的已存在则跳过（:53-62，幂等）。
- **进向量库（enableMemory :177-183）**：status→ENABLED 时，把 `{question, sideInfo, dbSchema, sql}` 打包成 langchain4j `TextSegment(question, metadata=exemplar 全字段 JSON)` → `embeddingService.addQuery(collection, ...)`；collection 名 = per-agent（EmbeddingConfig.java:32）。
- **删向量库（disableMemory :185-191）**：ENABLED→DISABLED/PENDING 或批量删除前先 `removeExemplar`。底层 `EmbeddingServiceImpl` 用 langchain4j `EmbeddingStoreFactoryProvider.create(collection)`，具体后端由 spring starter 选择（Milvus/pgvector/Chroma/OpenSearch/InMemory 可配）。
- **启动兜底**：CommandLineRunner `loadSysExemplars` 把所有 ENABLED 记忆重灌向量库（:221-241）；另有类路径 `s2-exemplar.json` 内置种子例句灌 `text2sql` collection（ExemplarServiceImpl.java:92-107）。

**MemoryReviewTask 评审落点**（memory/MemoryReviewTask.java）：@Scheduled 每 60s；只处理 llm_review 与 human_review **均为 null** 的行（:89-92）；LLM 输出正则 `opinion=(.*),.*comment=(.*)` 解析 → 写 **`llm_review`（POSITIVE/NEGATIVE）与 `llm_comment` 列**；**POSITIVE 直接置 status=ENABLED**（:124-127）→ updateMemory 内部触发 enableMemory 同步向量库。人工在 MemoryController 复核写 human_review/human_comment。

**检索**：`recallExemplars(collection, query, num)` → embeddingService.retrieveQuery → metadata 反序列化回 Text2SQLExemplar 并携带 similarity（ExemplarServiceImpl.java:66-84），作为 few-shot 进 prompt。

## 8. WrenAI：markdown 真相源 + LanceDB 可丢弃索引

**介质与格式**【核心】`core/wren/src/wren/memory/`

- 真相源：项目内 `knowledge/sql/*.md`，YAML frontmatter 字段 `nl / sql / source(默认 user) / created_at? / datasource? / tags?` + 下方自由正文（用户注释原样保留，markdown.py:112-139）；文件名 = NL 的确定性 slug（≤60 字符，同 NL 复用同文件、冲突加 `-2` 后缀，:32-37,96-109）。
- 派生索引：`~/.wren/memory/`（`_WREN_MEMORY_DIR`，store.py:25）LanceDB **两表**（Arrow schema :67-95）：
  - `schema_items(text, vector(f32×dim), item_type, model_name, item_name, data_type, expression, is_calculated, mdl_hash, indexed_at)`——从 MDL manifest 抽取的表/列/计算列项；
  - `query_history(text, vector, nl_query, sql_query, datasource, created_at, tags)`——NL→SQL 对，text=nl_query 的嵌入。
  - 换 embedding 模型导致维度不一致时**启动即报错**拒绝混写（:165-200）；tags 带 `origin:markdown-sync` 标记同步写入的行，forget 只删自己写的行防误删（:30-59）。

**向量化管线入口**：`MemoryStore.index_schema(manifest, replace=True, seed_queries=True)`（:210-265）——extract_schema_items → 批量 embed → 建表/替换；seed_queries 生成规范 NL-SQL 对（tag `source:seed`，只替换旧 seed、保留 user 行）。**索引重建入口**：Typer CLI `wren memory index|describe|fetch|store|recall|status|reset|check|watch`（cli.py:177-707）；`watch` 文件监听触发 `_reindex`。无 memory extra 时 CLI 检索降级为 grep markdown。

**store_query/recall_queries 落点**：MCP 工具 `store_query`（mcp_server.py:492-518）**先写 markdown 真相源**再 best-effort `MemoryStore.store_query`（失败仅 warning）；store_query 嵌入 NL 后 add 进 query_history（store.py:381-412）；recall_queries 向量 top-k（limit=3）+ `datasource='...'` SQL 式过滤（:414-438）。markdown↔索引双向同步：`load_queries`/`sync_markdown_queries`（:615,686）。

## 11. 设计结论（≤5 条）

1. **「markdown 为真相源、索引可丢弃」是被反复独立发明的同构**：WrenAI（"knowledge/ is durable, index is disposable"+origin 标记防误删）、Vibe-Trading（FTS5 空结果自动重建）、supersonic/dify（SQL 表真相源+启动重灌向量）四个互不相关的仓库都收敛到"派生索引坏了就重建、真相源永不丢"——对财务 agent 这是审计友好与运维简化的双赢，值得作为默认架构。
2. **原子写是文件记忆的最低门槛纪律**：TradingAgents temp+os.replace、Vibe flock+.lock、WrenAI sidecar 原子写各自实现了同构；凡走"读全文→内存改写→整文件替换"路径（无增量 append）就必须配原子替换，否则崩溃即损坏唯一真相源。
3. **结构化元数据放 tag 行/frontmatter 顶行，正文放自由文本**：TradingAgents 的 `[date|ticker|rating|...]` 首行、Vibe/agentscope/WrenAI 的 frontmatter——共同点是"机器解析只看头几行、人读正文不受干扰"；agentscope 更进一步把 description 定义为"检索触发条件"而非摘要，是文件记忆里最讲究的字段语义设计。
4. **双写的增量一致性靠状态机/标记位**：supersonic 用 status 迁移驱动向量增删、WrenAI 用 `origin:markdown-sync` tag 限定删除范围、dify 用 celery 异步任务+collection binding——凡 SQL+向量双写，必须显式回答"哪边是主、失步谁赢、删错怎么防"，三家给出了三种可抄的答案。
5. **向量 schema 的粒度选择有三种流派**：doc 内单向量列（crewAI）、独立向量表按字段一行（langgraph，支持同文档多字段索引+FK 级联）、metadata 全量 JSON 陪跑（supersonic langchain4j TextSegment）——字段级索引表是表达力最强的（多字段、CASCADE 删除、DISTINCT ON 去重），但 DDL 与迁移成本也最高，选型时按"是否需要对同一文档的不同片段分别检索"决策即可。
