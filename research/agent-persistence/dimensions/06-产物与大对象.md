# 06 产物与大对象存储（gemini-cli / opencode / DB-GPT / OpenHands / dify / data-formulator）

> agent-persistence 轮第 6 路。基线：gemini-cli@9c1b0a6105、opencode@95daf90670、DB-GPT@04559f9ccf、OpenHands@e8249f00a（经典锚点）、dify@79effdd498、data-formulator@5477f0e236。证据均为【核心】。

## 0. 综述

六仓对「产物与大对象」给出三类答案：**(a) 工具输出落盘指针**（gemini-cli / opencode / DB-GPT 新代）——超阈值全文写文件、上下文留「预览+路径」占位，模型用 read/grep 类工具按需取回；**(b) 结构化产物入列 + 大字段 offload**（DB-GPT 旧代 view message / dify workflow_node_executions）——用户可见产物作为独立消息/行落 DB，超大 JSON 卸到对象存储留引用；**(c) 工作区即数据湖**（OpenHands 沙箱 workspace / data-formulator workspace 目录）——产物就是文件系统本身，事件/状态里存路径或 base64。共同底线：**上下文只进小体积表示（占位/预览/路径），全文与二进制永远在上下文之外**；分歧在介质、是否可追溯（路径裸引用 vs 表+file_id 外键）与生命周期（无清理 / 7 天 TTL / 容器同生共死）。

## 8. 设计结论（面向财务 agent 参考架构）

1. **占位三件套是行业最小公约数**：尺寸声明（多大）、稳定指针（去哪取）、取回指引（用什么工具、怎么分段）。gemini-cli 的「头20%+尾80%」、opencode 的「头尾各半」、DB-GPT 的「前 1500 字符」证明 preview 只需够模型判断相关性，不必完整；财务报表场景可统一为「头 N 行 + 尾 N 行 + schema 摘要」。
2. **引用要外键化而非裸路径**：opencode 把 outputPath 升为 part schema 字段、dify 用 offload 行 → upload_files.id → storage key 三跳，都比裸绝对路径可治理（可迁介质、可 GC、可鉴权）。建议「消息 part 持 artifact_id，artifact 表持 storage key + hash + mime」，dify 的 sha3_256 内容哈希列顺带获得去重与完整性校验。
3. **防循环与降级路径必须显式**：DB-GPT 把 read_file 阈值 pin 到 inf 防 persist→read 死循环、写盘失败回落 inline 截断；gemini-cli 压缩期落盘失败保留原文。落盘指针是 I/O 依赖，设计时就要定义「存不下去时上下文怎么办」（截断而非报错）。
4. **两层预算优于单阈值**：DB-GPT 的 L2（单结果 100K 字符）+ L3（单轮聚合 200K）与 gemini-cli 的「工具输出阈值 + 压缩期 50K token 反向预算」都认识到：只限单条会被数量击穿。阈值还应随模型窗口缩放（DB-GPT 15% 窗口占比 + floor/cap 钳制是现成公式）。
5. **生命周期是被普遍欠账的一环**：六仓中仅 opencode（7 天 TTL）和 data-formulator（工作区 TTL/LRU）有真清理；gemini-cli/DB-GPT 无限累积、OpenHands 依赖容器销毁。产物存储从第一天就该带 owner（会话/租户外键）+ 保留期 + 无主标记（dify 的 node_execution_id=NULL GC 候选是轻量做法），否则审计库会变成成本中心。
